## 1. Specification vs. Implementation

**Current Specification (Constitution):**
"Multi-TF (MTF) breakouts must be confirmed across four timeframes: Daily, Hourly, 15m, 5m. For Phase A (Hourly Confirmation), the hourly RSI must be strictly greater than 60 to confirm momentum."

**Current Implementation (`app/multi_tf_scanner.py`):**
In `run_hourly_phase()` and the scanner ladder, RSI is checked and passed down to the final `TRADE_ACTIVE` alert payload (so it is evaluated later for analytics), but an `RSI > 60` gate is missing entirely from the phase transition logics (e.g. `HOURLY_APPROVED`). The Phase A gate relies solely on EMA/ADX and proximity to the breakout level.

## 2. Evidence & Findings

- **Code Location:** `app/multi_tf_scanner.py` (`run_hourly_phase` / `run_lower_tf_phase`)
- **Historical Context:** RSI > 60 does not appear to be enforced indirectly via any shared helpers or indicators. It is simply tracked but not utilized as an execution gate. 
- **Operational Impact:** Allowing setups with `RSI < 60` to proceed through the MTF ladder may result in low-momentum breakouts generating alerts, causing increased false breakouts or chop.

## 3. Governance Assessment

**Classification:** Specification/Implementation Drift

**Questions for Review:**
1. Was the RSI gate intentionally removed to increase MTF trade volume?
2. If yes, should the Constitution be amended (Level 4 Change) to remove the strict `RSI > 60` requirement?
3. If no, this is a clear bug. Should the codebase be modified (Level 3 Change) to insert `latest["RSI"] > 60` into the hourly and sub-hourly phase transitions?

## 4. Decision
**Status:** Pending Review
**Recommendation:** Most likely a true Level 3 Implementation Change to fix a missing validation gate, pending confirmation.
